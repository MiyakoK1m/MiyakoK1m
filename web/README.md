# Заселение и аренда — веб-версия

Браузерный компаньон к Android-приложению: тот же REST API, к которому ходит и телефон, так что
запись, добавленная с компьютера, тут же видна в приложении (и наоборот). Node.js 22+ (встроенный
`node:sqlite`), без npm-зависимостей на бэкенде; фронтенд — обычный HTML/CSS/JS (без сборки),
экспорт/импорт Excel — через самостоятельно захостенный SheetJS (`public/js/xlsx.full.min.js`).

## Запуск локально

```bash
cd web
node server.js
# откройте http://localhost:3000
```

Данные хранятся в `web/rental.db` (создаётся автоматически), загруженные чеки — в `web/uploads/`.

## Деплой на Render.com (рекомендуется)

В репозитории уже лежит `render.yaml` (в корне репозитория, не в `web/`) — это Render Blueprint,
описывающий сервис целиком.

1. Зарегистрируйтесь на [render.com](https://render.com) (проще всего — через GitHub).
2. **New +** → **Blueprint**.
3. Выберите этот репозиторий (и нужную ветку — например `claude/new-session-o6xs1b`, пока это не
   влилось в основную ветку).
4. Render прочитает `render.yaml` и предложит создать веб-сервис `hr-housing-web` — подтвердите.
5. Дождитесь окончания деплоя (несколько минут на первый билд) — Render покажет публичный адрес
   вида `https://hr-housing-web.onrender.com`.
6. Откройте этот адрес в браузере — это и есть сайт для заполнения с компьютера.
7. В Android-приложении в разделе «Настройки» укажите этот же адрес — тогда телефон будет читать и
   писать в ту же базу, что и сайт.

### Почему план не бесплатный

`render.yaml` просит план **Starter** (~$7/мес), потому что к сервису подключён постоянный диск
(`disk:` в манифесте) — там лежит файл SQLite и загруженные чеки. На бесплatном тарифе Render диск
не сохраняется между перезапусками контейнера (а перезапуски там случаются регулярно, в том числе
просто от «сна» после периода без запросов) — значит, реальные данные HR периодически бы стирались.
Если это неприемлемо по бюджету — самый простой запасной вариант: тот же сервер, но без диска,
плюс регулярная «Резервное копирование» кнопка (раздел «База данных») как ручной бэкап перед сном
сервиса; либо перенести хранение на внешнюю БД с постоянным бесплатным тиром (например Turso/
LibSQL) — это отдельная переделка `server.js`, дайте знать, если нужно.

## REST API (кратко)

Все ресурсы, кроме `shared-fields`/`templates`, — обычный CRUD над JSON-объектами, повторяющими
поля Kotlin-моделей Android-приложения один в один:

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/trip-entries` | Список записей «Входная информация» |
| POST | `/api/trip-entries` | Создать запись |
| PUT | `/api/trip-entries/:id` | Обновить запись |
| DELETE | `/api/trip-entries/:id` | Удалить запись |
| GET/POST/PUT/DELETE | `/api/rental-records[...]` | То же для «База данных» аренды |
| GET/POST/PUT/DELETE | `/api/landlords[...]` | Арендодатели |
| GET/POST/PUT/DELETE | `/api/residents[...]` | Проживающие сотрудники |
| GET/POST/DELETE | `/api/cities[...]` | Города |
| POST | `/api/cities-reset` | Сбросить города к списку по умолчанию |
| GET/POST/DELETE | `/api/finance-registry[...]` | Реестр согласований с финансами |
| GET | `/api/shared-fields` | Текущее состояние «сквозных» полей (ФИО/город/даты/…) |
| PUT | `/api/shared-fields` | Частичное обновление (merge) |
| GET | `/api/templates` | Все три редактируемых шаблона текста |
| PUT | `/api/templates/:key` | Обновить один шаблон (`CHECKIN`/`BOOKING`/`FINANCE_OBJECT`) |
| POST | `/api/upload` | Загрузить файл чека (тело — сырые байты, заголовок `X-Original-Filename`) |
| DELETE | `/api/all-data` | Полная очистка (аналог кнопки «Удалить все данные») |

## Тестирование

Весь фронтенд прогнан через headless Chromium (Playwright) с реальными кликами по всем 11
разделам плюс сквозным round-trip тестом парсинга Excel-заголовков — это не Claude Artifact, а
обычный сайт, так что тестировался по-настоящему, а не только на глаз.
